# Spec: USD budgets (RateGuard 0.6)

Status: **stage A implemented 2026-11-12** in all three SDKs (commit `b4dbc2b`): config, money
math, reserve and settle on every outbound call, the two 429 codes, the unpriced rule, the read API,
conformance vectors, mutants. **Stage B, 2026-11-12:** MCP `get_usd_budget`, `usd_budget` in
`list_limits` and admin state, the two Prometheus counters. **Not built yet:** the span attribute,
the realtime commit and a Redis store (sections 6.2, 8 and 9). Owner decisions:
keep counting cached prompt tokens in token budgets (2026-11-11); D1 deny, D2 customer, D3 USD in
config and micro-USD elsewhere (2026-11-12, the recommendations).
Implements in all three SDKs in one change (AGENTS.md rule 1), with conformance vectors (rule 13).

## 1. The problem in one paragraph

A token budget answers "how many tokens may this key use". The person paying asks "how many
dollars". Across the 65 rows of `conformance/pricing.json` a token costs anywhere from $0.05/M
(gpt-5-nano input) to $600/M (o1-pro output), a 12,000x spread; between two current models, a
GPT-6 Luna input token ($0.10/M) and a Claude Fable 5.1 output token ($50/M) differ 500x. Within
one model a cache read costs a tenth of a fresh token while a 1-hour cache write costs twice. A team that sets a
token budget to protect a bill is guessing the exchange rate. 0.6 lets them state the bill.

## 2. What others do (checked 2026-11-11, `bolting/bin/research`)

| Product | Unit | When cost is counted | Consequence |
|---|---|---|---|
| LiteLLM proxy | USD `max_budget`, `soft_budget`, `budget_duration` per key/user/team | after the response | concurrent bursts overshoot before spend updates; an open bug (BerriAI/litellm#26672, 2026-04-28) reports key and user `max_budget` not enforced at all on v1.82.3 |
| Kong AI Rate Limiting Advanced (cost strategy) | USD per consumer group, per window | after the response; Kong's docs say the cost "is only reflected during the next request" | the request that crosses the line always completes |
| Portkey | USD or tokens per virtual key, periodic reset, $1 minimum | after usage is recorded; the key expires when the limit is reached | same post-hoc window |
| OpenRouter | credits per API key | during the stream: a crossed limit arrives as an SSE chunk with `finish_reason: "error"` inside an HTTP 200 | callers must parse chunks to notice |
| OpenTelemetry GenAI semconv | tokens only | n/a | there is **no** standard cost attribute: the `gen_ai.usage.*` registry has input, output, reasoning and cache-read token counts. A blog's `gen_ai.usage.cost` is not in the spec |

The common shape is **post-hoc settlement**: spend is debited after the response, so a key's
budget is a soft line that concurrency and long outputs cross. RateGuard's token budget already
does better: it **reserves a measured estimate before the call** (prompt tokens plus the declared
output ceiling, `core/request-estimate.ts`) and settles to the real usage after. 0.6 applies the
same reserve-then-settle to dollars. That is the feature: a dollar line that a burst of concurrent
calls cannot cross by more than the error in their own estimates.

## 3. Decision class

- **One-way door:** the public config names and the wire format of the new 429 error code, the
  money unit in events/receipts, and what an unpriced model does by default. These are written
  down here and in the conformance vectors before any code.
- **Two-way door:** the reservation formula, window bookkeeping, metric names. Changeable in a patch.
- **A principle changes.** `genai.ts` says costs "are observability estimates only; they never drive
  enforcement". 0.6 makes them drive enforcement **when a USD budget is configured**, and only
  then. The estimate is still an estimate: RateGuard enforces on what its price table says was
  spent, never on the provider's invoice. Every surface says "estimated USD" (sections 8, 9).

## 4. Configuration

```ts
// Node (Go: Config.USDBudget, Python: usd_budget=)
new RateGuard({
  usdBudget: {
    hourLimitUSD?: number,   // e.g. 5.00
    dayLimitUSD?: number,
    monthLimitUSD?: number,
    mode?: 'hard-stop' | 'soft-stop',   // same meaning as tokenBudget.mode
    softStopAt?: number,                 // fraction, default 0.8 (as tokenBudget)
    scope?: 'tenant' | 'customer' | 'model',   // DECISION D2, default 'customer'
    unpriced?: 'deny' | 'allow-uncounted',     // DECISION D1, default 'deny'
  },
  pricing?: PricingProvider,  // existing seam; consulted before the built-in table
})
```

- Limits are given in USD for people and converted **once, at config load**, to integer
  micro-USD (`Math.round(usd * 1_000_000)`). Every comparison and stored value after that is an
  integer, the unit spend receipts already use (`core/spend-receipt.ts`). No float ever crosses
  an SDK boundary, which is what keeps three languages byte-identical.
- A USD budget and a token budget may both be set. Each is checked; either can deny.
- Validation: a negative or non-finite limit, an unknown scope or an unknown `unpriced` value is a
  config error: Node throws, Python raises `ValueError`, Go's `New` panics (Go has no error return
  there; a money limit that is silently off is worse). Go callers can check with
  `USDBudget.Validate()` first. All-zero limits leave the budget off.

## 5. Keys and scope (decision D2)

Token budgets key on `tenant[:customer=X]:provider:model:outbound`, because tokens of different
models are not comparable. Dollars are, and comparing across models is the point of a dollar
budget. So the USD budget key drops provider and model:

| scope | key | meaning |
|---|---|---|
| `tenant` | `tenant:usd` | one bill for the whole process |
| `customer` (default) | `tenant[:customer=X]:usd` | one bill per end customer when the customer header is present, else per tenant |
| `model` | `tenant[:customer=X]:provider:model:usd` | parity with token budgets, for people who price per model |

Fallback across providers (`provider-chain.ts`) debits the same `customer` key whichever provider
answered, which is what the payer expects.

## 6. Reservation and settlement

### 6.1 Reserve (before the call)

```
price      = pricing.priceFor(model) ?? builtin(model, promptTokensEstimate)   // long-context row chosen on the estimate
inRate     = max(price.input, price.cacheWrite, price.cacheWriteLongTTL)   always (see below)
reserveUSD = promptTokensEstimate * inRate + outputCeiling * price.output   (per 1M, then to micro-USD, ceil)
```

- `promptTokensEstimate` and `outputCeiling` are the numbers the token budget already measures
  (`estimateRequestTokens`: prompt tokens plus `max_tokens` / `max_completion_tokens` /
  `maxOutputTokens`, or the documented allowance when the request declares none).
- The input side is priced at the **highest** input rate the request could be billed at, so a
  cache write premium (Anthropic 1.25x for 5 minutes, 2x for 1 hour) cannot make the real cost
  exceed the reservation. A cache read is always cheaper than input, so it never can.
  *Changed in implementation:* the draft priced at `input` unless the request asked for caching.
  OpenAI caches automatically and bills writes on some models without the request saying so, and
  detecting "asked for caching" per provider would be a fourth parser to keep in parity. Always
  using the dearest rate over-reserves slightly (costs concurrency, never money).
- Long context: if the estimate is over `longContext.aboveTokens`, the whole reservation uses the
  long-context rates, matching how vendors bill.
- Rounding: **ceil** to the next micro-USD. A reservation is a bound; rounding it down would let
  many tiny calls each slip a fraction under.
- Same `estimatedTokens` override as today: a positive value pins the token estimate; negative
  means reserve-all (the whole remaining USD budget), one call in flight per key.

If the reservation does not fit in the remaining budget of any window, hard-stop denies with the
429 in section 7 and nothing is sent upstream.

### 6.2 Settle (after the call)

```
actualUSD = estimateUsageCost(model, usage)   // fresh*input + read*cacheRead + write*cacheWrite + writeLong*cacheWriteLongTTL + output*output
commit    = ceil_micro(actualUSD)
```

- Settlement uses the merged usage the token budget already trusts: streaming usage is merged per
  event with MAX semantics (AGENTS.md rule 12), so Groq's triple usage emission is not billed 3x.
- **When usage cannot be measured** (a stream without `include_usage`, an over-cap body, an
  unknown schema) the **reservation is committed**, exactly as the token budget commits its
  reserved estimate today. Recording zero would let a runaway agent spend without touching its
  budget.
- A failed call (network error, 5xx that triggers fallback) releases its reservation; the
  fallback attempt makes its own.
- Realtime sessions (`core/realtime.ts`) already carry a caller-priced cost limit per session;
  0.6 does not merge the two. A realtime guard's estimated cost may be committed to the USD
  budget at session end (`commitRealtime`), listed as a follow-up, not in 0.6.

### 6.3 Overshoot bound

With reservations sized from the request, total committed spend can exceed a window's limit only
by the sum, over calls in flight, of (actual cost - reserved cost) where actual > reserved. Since
the input side is reserved at the highest input rate and the output side at the declared ceiling,
that difference is non-zero only when the prompt-token estimate under-counts. Same bound as the
token budget (`request-estimate.ts`: `overshoot <= limit * (actual / estimate)`). It is written
into the conformance vectors as a test, not just this sentence.

## 7. When a call is denied

- HTTP 429, provider-native error body (the same synthesis as `token_budget_exceeded`, so SDK
  retry logic keeps working), error code **`usd_budget_exceeded`**, `retry-after` from the window
  that denied, `RateLimit-*` headers as today.
- Message names the window and says "estimated": `rateguard: estimated USD budget exhausted for
  customer X (day window)`.
- Soft-stop: the call proceeds; a `usd_budget_warning` event fires once per window crossing of
  `softStopAt`.
- Unpriced model (decision D1): with `unpriced: 'deny'` (default) a call to a model neither the
  caller's `PricingProvider` nor the built-in table can price is denied with 429 code
  **`usd_price_unknown`**, not sent. The message names the model and says how to price it. With
  `'allow-uncounted'` it is sent, counted as zero, and an `usd_unpriced_call` event fires every
  time (never silently).

## 8. What a user sees

- MCP: a new tool **`get_usd_budget`** (peek, never reserves), and `list_limits` gains the USD
  windows. That is 8 tools; the parity guard's capability list and the README count change.
- Admin API: `GET /admin/state` includes `usd_budget: { window, limit_micro_usd, used_micro_usd,
  reserved_micro_usd, remaining_micro_usd }`.
- Prometheus: `rateguard_usd_budget_spent_micro_usd_total`, `rateguard_usd_budget_exhausted_total`,
  `rateguard_usd_unpriced_calls_total`.
- OpenTelemetry: there is no standard cost attribute, so RateGuard uses its own namespace on the
  GenAI span: `rateguard.cost.estimated_micro_usd` (integer). It does not invent a `gen_ai.*` key.
- Spend receipts and FOCUS export are unchanged: they already carry `estimated_cost_micro_usd`,
  and `BilledCost` stays 0, because an estimate is never presented as invoice truth.

## 9. Honest limits (to state in the README)

1. It enforces on RateGuard's price table, dated and sourced, not on the provider's invoice. A
   stale or wrong row makes the budget wrong in the same direction. CI already fails a table
   that is unreviewed for 90 days or past a `priceChangesOn` date.
2. The table is the standard tier. Batch calls are over-counted (safe). **Priority or
   provisioned tiers are under-counted** (unsafe): a user on those tiers should supply a
   `PricingProvider` with their rates. The README must say this in the first USD-budget paragraph.
3. Tokenizer drift: Claude 4.7 and later produce about 30% more tokens for the same text. This
   only affects the reservation estimate; settlement uses the provider's own token counts.
4. In-memory per process, as the token budget is today. Several replicas each enforce their own
   line. A Redis-backed USD store follows the generalized-cost `Increment` script already in all
   three SDKs; it is a 0.6.x item, not 0.6.0.

## 10. Conformance vectors (`conformance/usd_budget_vectors.json`)

One file, replayed by all three SDKs (`TestConformanceUSDBudget`, `conformance.test.ts`,
`test_conformance.py`), pinned against a frozen copy of four price rows inside the file (so a
price-table update never changes a vector):

1. Config conversion: `0.1 USD` → `100000` micro; `5e-7 USD` → `1` (round).
2. Reservation: prompt 10,000, ceiling 1,000, no caching → exact micro-USD; same with caching
   requested → priced at the cache-write rate; prompt over `aboveTokens` → long-context rates.
3. Ceil: a reservation of 0.0000014 USD → 2 micro, not 1.
4. Settlement: usage with cache read, cache write and long-TTL write → exact micro-USD.
5. Sequence: limit 1,000 micro; reserve 600 (allow, 400 left); reserve 600 (allowed, holds the
   remaining 400: the token budget's shipped rule is reserve min(estimate, remaining) and deny only
   at zero, and the draft's "deny" contradicted it); reserve 1 (deny); settle the first at 300;
   release the second; then 700 left. Single window only: Go and Node choose the active window
   differently when several are set.
6. Unmeasurable usage commits the reservation.
7. Unpriced model: `deny` → `usd_price_unknown`, nothing reserved; `allow-uncounted` → allowed,
   0 committed, event emitted.
8. Scope: two models under `customer` scope draw from one key; under `model` scope, two.
9. Overshoot: N concurrent reservations whose estimates under-count by a stated ratio end within
   the documented bound.

## 13. Decisions for Harsha (recommendation first)

- **D1. Unpriced model under a USD budget.** *Recommend `deny` by default.* A budget that waves
  through the models it cannot price is the denial-of-wallet hole RateGuard exists to close.
  Cost: a new model breaks until its row is added or a `PricingProvider` prices it, which is loud
  and fixable in one line. Alternative `allow-uncounted` is offered, never silent.
- **D2. Default scope.** *Recommend `customer`* (tenant when no customer header). It matches who
  pays, and it is what LiteLLM and Portkey users expect (per key/user/team). `model` scope stays
  available for parity with token budgets.
- **D3. Public unit.** *Recommend USD decimals in config, integer micro-USD everywhere else.*
  People write dollars; three languages agree only on integers.
